Strona, która działa jak aplikacja

Wzorce prezentacji i interakcji, które sprawiają, że strona czuje się jak apka, a nie jak statyczny dokument: przełączniki przy tabelach, przejścia między widokami, skeletony zamiast spinnerów, optimistic UI, stories, swipe, FAB i PWA. Każdy wzorzec z działającym demo i kodem.

To kontynuacja „Specyfikacji Optymalizacji Mobile". Tam: fundamenty, wydajność, dostępność. Tu: wzorce, które dają uczucie apki. Otwórz na telefonie i testuj dotykiem.

Fundament

0 · Co odróżnia „apkę" od „strony"

Różnica nie leży w technologii, tylko w odczuciu. Strona-dokument: klikasz → biały ekran → przeładowanie → nowa strona. Apka: dotykasz → natychmiastowa reakcja → treść zmienia się płynnie w miejscu. Pięć zasad, które budują to uczucie:

  • Natychmiastowy feedback — każde dotknięcie ma reakcję w <100ms (stan :active, podświetlenie, skala)
  • Brak „białych przeładowań" — treść zmienia się w miejscu (przełączniki, taby, przejścia), nie przez reload całej strony
  • Ruch z sensem — animacja pokazuje skąd-dokąd (element się przesuwa, panel wjeżdża), nie ozdabia
  • Stan jest zachowany — wracasz tam, gdzie byłeś; scroll, filtr, zakładka pamiętane
  • Treść zanim dane — skeleton/optimistic zamiast pustego spinnera; interfejs „wyprzedza" serwer
Klucz psychologiczny: chodzi o perceived performance — postrzeganą szybkość. Apka nie jest szybsza technicznie; po prostu nigdy nie zostawia użytkownika z pustym ekranem bez reakcji.

Kod — segmented control z animowaną „pigułką"

<div class="seg" id="seg">
  <span class="pill"></span>
  <button class="on" data-mode="m">Miesięcznie</button>
  <button data-mode="y">Rocznie</button>

const seg = document.getElementById('seg');
const pill = seg.querySelector('.pill');
function move(btn){                          // przesuń pigułkę pod aktywny
  pill.style.left = btn.offsetLeft + 'px';
  pill.style.width = btn.offsetWidth + 'px';
}
seg.querySelectorAll('button').forEach(b => b.onclick = () => {
  seg.querySelectorAll('button').forEach(x => x.classList.remove('on'));
  b.classList.add('on'); move(b);
  updateTable(b.dataset.mode);            // podmień dane w miejscu — bez reloadu
});
✓ Rób

  • Zmiana treści w miejscu, bez przeładowania strony
  • Pamiętaj wybór (localStorage / URL ?plan=y)
  • Pokaż korzyść przy przełączeniu (badge „−20%", „oszczędzasz")

  • Niejasnego stanu — który wariant jest aktywny?
  • Skoków layoutu gdy zmienia się długość treści

2 · Przestrzeń i oddech — ile realnie masz miejsca

Telefon ma dużo mniej użytecznej przestrzeni, niż mówi przekątna. Z ekranu zjada pasek przeglądarki, safe area (notch, pasek gestów), a przy formularzu — klawiatura. Trzeba projektować pod realną wysokość, nie teoretyczną.

3 · Skracanie scrolla — żeby nie przewijać „5 minut"

Oddech tak, ale nie kosztem 10-ekranowej ściany. Cel: użytkownik dociera do tego, czego szuka, w 2–3 ruchach kciuka, a nie po minucie scrollowania. Sztuka to gęstość sterowana — pokazuj mało, ale daj szybki dostęp do reszty. To samo serce co „app-like": treść na żądanie, nie wszystko naraz.

4 · Duże elementy desktopowe → mobile

Najtrudniejsze w RWD to nie tekst, tylko „ciężkie" komponenty desktopowe: mega-menu, szerokie tabele, wielokolumnowe sekcje, sidebary, najazdy hover. Nie skaluj ich w dół — przekształć w mobilny odpowiednik.

Ruch & nawigacja

6 · Przejścia między widokami Baseline 2025

Największy „przeskok" z dokumentu do apki: zamiast białego mignięcia przy zmianie treści/strony — płynna animacja, w której elementy się przesuwają, a obraz produktu „rośnie" w widok szczegółów. Robi to View Transitions API — natywnie, bez bibliotek.

  • Same-document (zmiana treści w SPA) — Baseline od października 2025, działa we wszystkich silnikach
  • Cross-document (między stronami MPA) — Chrome/Edge 126+ i Safari 18.2+; Firefox jeszcze nie
  • Progresywnie — gdy brak wsparcia, treść po prostu zmienia się bez animacji (nic się nie psuje)
Demo — kliknij, treść zmieni się z animacją (jeśli przeglądarka wspiera)

Widok: Lista

To jest pierwszy widok. Kliknij przycisk, żeby przejść do szczegółów — z płynnym przejściem.

Kod — same-document, z bezpiecznym fallbackiem

function swap(updateDOM){
  // jeśli brak wsparcia — po prostu zmień DOM, bez animacji
  if(!document.startViewTransition){ updateDOM(); return; }
  document.startViewTransition(updateDOM);   // animowane przejście
}
/* „shared element" — ten sam obraz płynnie łączy dwa widoki */
.product-img{ view-transition-name: hero-photo; }
/* dla MPA wystarczy jedna reguła w CSS: */
@view-transition{ navigation: auto; }
Z umiarem: przejścia mają komunikować nawigację (skąd-dokąd), nie efekciarstwo. Trzymaj 200–300ms i respektuj prefers-reduced-motion.

8 · Animacje sterowane scrollem ~85% wsparcia

Elementy pojawiają się/poruszają wraz z przewijaniem — pasek postępu czytania, „wjeżdżające" sekcje, parallax. Nowość: robi to czysty CSS (animation-timeline), bez JS i bez kosztu wydajności scrolla. Wsparcie ~85% (Chromium + Safari; Firefox za flagą) — używaj jako progressive enhancement.

Demo — pasek postępu u góry rośnie wraz ze scrollem strony

Spójrz na samą górę tej strony podczas przewijania — fioletowy pasek pokazuje postęp czytania (zbudowany techniką poniżej).

Kod — pasek postępu czytania (zero JS)

.progress{
  position: fixed; top:0; left:0; height:3px; width:100%;
  transform-origin: left;
  animation: grow linear;
  animation-timeline: scroll(root);   /* oś = scroll strony */
}
@keyframes grow{ from{ transform:scaleX(0); } to{ transform:scaleX(1); } }
/* „wjazd" sekcji gdy wchodzi w ekran */
.reveal{
  animation: fadeUp linear both;
  animation-timeline: view();            /* oś = widoczność elementu */
  animation-range: entry 0% cover 30%;
}
Progressive enhancement: zawsze projektuj tak, by bez wsparcia treść była widoczna (animacja tylko „dodaje"). Nie ukrywaj treści, którą pokazuje dopiero animacja — w Firefoksie zniknie.
Czas & feedback

9 · Skeleton & stany ładowania

Pusty ekran ze spinnerem = „czekaj, nie wiem co się dzieje". Skeleton (szary zarys układu) = „treść już się buduje". Badania: użytkownicy odbierają strony ze skeletonem jako ~30% szybsze przy tym samym realnym czasie. Pokaż go w <300ms od akcji.

Krótka akcja blokująca (zapis, login, płatność)Spinner na przycisku

  • Skeleton ≈ realny układ — te same kształty/rozmiary, żeby nie było skoku przy podmianie
  • Dostępność — aria-busy="true" na kontenerze, prefers-reduced-motion wyłącza shimmer
  • Nie nadużywaj — dla <300ms operacji lepiej nic nie pokazywać niż migać skeletonem
Czas & feedback

10 · Optimistic UI — interfejs „wyprzedza" serwer

Najbardziej „apkowe" odczucie: tapiesz serduszko i ono od razu jest czerwone — interfejs nie czeka na serwer, zakłada sukces i tylko cofa zmianę, jeśli coś padnie. Idealne do częstych, niskiego ryzyka akcji: like, zapis, zaznacz, przełącz, dodaj do ulubionych.

Demo — kliknij, reakcja jest natychmiastowa (0ms czekania)

Stan zmienia się od razu. W realu w tle leci zapis; gdyby się nie udał — cofamy i pokazujemy toast „nie udało się".

Wzorzec

async function toggleLike(){
  const prev = state.liked;
  render(!prev);                 // 1. ZMIEŃ UI OD RAZU (optymistycznie)
  try{
    await api.setLike(!prev);     // 2. wyślij w tle
  }catch(e){
    render(prev);               // 3. błąd → cofnij
    toast('Nie udało się — spróbuj ponownie');
  }
}
Tylko niskie ryzyko. Nie rób optymistycznie płatności, usuwania konta ani rzeczy, których cofnięcie jest mylące. Tam: spinner + jasne potwierdzenie.
Czas & feedback

11 · Toast / snackbar — feedback bez blokowania

Krótki komunikat u dołu, który nie zatrzymuje pracy i sam znika. Zastępuje natrętne alert() i przeładowania „zapisano". Toast = sama informacja; snackbar = informacja + akcja (np. „Cofnij").

Demo — kliknij, pojawi się snackbar z akcją „Cofnij"
  • Pozycja — dół ekranu (strefa kciuka, nie zasłania treści u góry)
  • Czas — 4–6s auto-znikanie; z akcją dłużej; krytyczne błędy NIE jako toast
  • Jeden na raz — kolejkuj, nie zasypuj; wejście ≤300ms
  • Dostępność — role="status" / aria-live="polite", akcja osiągalna z klawiatury

12 · Microinteractions & haptyka

Drobne reakcje, które potwierdzają „zadziałało": przycisk lekko się wciska, ikona pulsuje, telefon delikatnie wibruje. Pojedynczo niewidoczne, razem dają wrażenie „żywego", responsywnego interfejsu. Reguła: ≤300ms, zawsze z sensem.

13 · Stories / sekcje pełnoekranowe

14 · Swipe actions — gest na elemencie listy

Przesuń wiersz w lewo → odsłania się akcja (usuń, archiwizuj). Szybkie i „apkowe", jak w mailu czy liście zadań. Zasada bezpieczeństwa: gest to skrót, ale musi być też zwykły przycisk (gest jest niewidoczny).

15 · FAB & pull-to-refresh

FAB (floating action button) — okrągły przycisk głównej akcji, „pływający" nad treścią w zasięgu kciuka. Jedna, najważniejsza akcja ekranu (napisz, dodaj, +). Może rozwijać 2–4 akcje.

Pull-to-refresh — odświeżanie gestem

Pociągnięcie listy w dół = odśwież. Oczekiwane w feedach (maile, social, powiadomienia). Daje poczucie kontroli i świeżości treści.

  • FAB: jedna akcja — najważniejsza na ekranie; nie rób z niego śmietnika opcji
  • Nie zasłaniaj nim treści ani innych CTA; trzymaj nad bottom nav
  • Pull-to-refresh z feedbackiem (spinner napina się z gestem) i lekką wibracją na wyzwoleniu
  • Tylko dla feedów — nie podpinaj go pod statyczne strony ofertowe

16 · Natywne API — możliwości jak w apce

Przeglądarka mobilna ma dostęp do funkcji systemu, które dają „apkowe" możliwości. Zasada: feature detection + graceful degradation — sprawdź czy API istnieje, a jak nie, daj fallback. Nic się nie psuje na niewspieranych urządzeniach.

Bajery & opakowanie

17 · PWA — strona instalowalna jak apka

Progressive Web App to strona, którą można dodać do ekranu głównego: własna ikona, uruchamia się pełnoekranowo (bez paska przeglądarki), działa offline. Wygląda i otwiera się jak natywna apka — bez App Store. Wymaga HTTPS, manifestu i service workera.

1 · Manifest (jak apka ma wyglądać)

// manifest.webmanifest
{
  "name": "agency-site",
  "short_name": "agency-site",
  "start_url": "/",
  "display": "standalone",        // pełny ekran, bez UI przeglądarki
  "background_color": "#0b0e14",
  "theme_color": "#6c8cff",
  "icons": [{ "src":"/icon-512.png", "sizes":"512x512", "type":"image/png" }]
}

2 · Service worker (offline + szybki start)

// rejestracja w stronie
if('serviceWorker' in navigator) navigator.serviceWorker.register('/sw.js');
// sw.js — cache podstaw, by działało offline
self.addEventListener('fetch', e => {
  e.respondWith(caches.match(e.request).then(r => r || fetch(e.request)));
});
✓ Rób
  • display: standalone + ikona + theme color = natywny wygląd
  • Cache app shell — natychmiastowy start, offline fallback
  • Audyt w Lighthouse (zakładka PWA / installability)
✕ Pamiętaj
  • iOS nie ma auto-promptu — pokaż własny baner „Dodaj do ekranu" z instrukcją
  • Bez HTTPS PWA nie zadziała
  • Web Push na iOS tylko po instalacji jako PWA (16.4+)
Android potrafi sam zaproponować instalację (zdarzenie beforeinstallprompt — możesz pokazać własny przycisk). iOS wymaga ręcznego „Udostępnij → Do ekranu początkowego", więc dodaj edukacyjną podpowiedź tylko dla Safari iOS.

18 · Jak weryfikować, testować i zmieniać

Nie zgaduj — mierz. Pętla: zmierz → postaw hipotezę → zmień jedną rzecz → zmierz ponownie. Lab (Lighthouse) pokazuje potencjał, ale prawdę mówi realny ruch (field data) i realne urządzenie.

Co realnie sprawdzać na mobile

  • Scroll-depth (heatmapa) — jak głęboko ludzie docierają? Jeśli 80% nie widzi CTA → skróć/przenieś wyżej (sekcja 3)
  • Tap heatmapa — gdzie klikają? Mis-tapy = za małe/za blisko cele (sprawdź 44–48px)
  • Nagrania sesji — gdzie się gubią, gdzie „rage taps" (wściekłe wielokrotne tapnięcia)
  • Throttling — testuj na „Slow 4G" + CPU 4× slowdown; to realność, nie WiFi na MacBooku
  • Formularz z klawiaturą — czy pole i przycisk mieszczą się nad klawiaturą (sekcja 2)
  • A/B test jednej zmiany naraz — inaczej nie wiesz, co zadziałało
Pętla iteracji: heatmapa/nagranie pokazuje problem → stawiasz hipotezę → zmieniasz jedną rzecz → A/B lub kolejny pomiar potwierdza. Małe, mierzone kroki biją wielki redesign „na czuja".
Jakość

19 · Checklist „app-like"

Uczucie apki

  • Każde tapnięcie ma feedback <100ms (:active, podświetlenie)
  • Zmiany treści w miejscu (toggle/taby/View Transitions), nie przez reload
  • Skeleton dla ładowania treści, optimistic UI dla like/zapis
  • Feedback przez toast/snackbar, nie alert()
  • Stały app shell (nagłówek + bottom nav), stan zachowany

Przestrzeń & scroll

  • Projekt pod realną wysokość (~660px), formularz testowany z klawiaturą
  • Odstępy w skali 8pt, gutter 16–24px, nic nie dotyka krawędzi
  • Kluczowa treść + CTA w pierwszych 1–2 ekranach
  • Długie treści zwinięte (akordeon/taby) — bez „5-minutowego scrolla"

Adaptacja desktopu

  • Mega-menu → hamburger/bottom nav; sidebar → bottom sheet
  • Szerokie tabele → karty lub scroll z przyklejoną kolumną
  • Hover → tap (na dotyku nie ma hover); wielokolumny → stack wg priorytetu

Bajery & jakość

  • Natywne API z feature detection (Web Share, capture, Pay, wake lock)
  • PWA: manifest + service worker + HTTPS, audyt Lighthouse
  • Wszystkie animacje respektują prefers-reduced-motion
  • Przetestowane na realnym telefonie + throttling + heatmapa scroll-depth
