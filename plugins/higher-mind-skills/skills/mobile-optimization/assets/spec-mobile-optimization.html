Optymalizacja stron pod mobile

Kompletna specyfikacja wzorców, liczb i kodu — od fundamentów (viewport, breakpointy) przez wzorce interakcji (przewijanie w prawo, rozwijane elementy, bottom sheet) po wydajność i dostępność. Każdy wzorzec ma działające demo i gotowy do skopiowania kod.

Fundamenty

1 · Mobile-first & viewport

Ponad 60% globalnego ruchu to mobile, a Google indeksuje stronę w wersji mobilnej (mobile-first indexing). Zasada: projektujesz i piszesz CSS najpierw na telefon, a większe ekrany dodajesz przez min-width. Bazowy CSS jest wtedy prostszy i lżejszy dla słabszych urządzeń, a desktop tylko go rozszerza.

Viewport meta — bez tego nic nie działa

Pierwsza linia każdego <head>. Bez niej mobilna przeglądarka renderuje stronę jak desktop (~980px) i skaluje w dół.

<meta name="viewport" content="width=device-width, initial-scale=1.0">
Nie blokuj zoomu. maximum-scale=1 lub user-scalable=no łamie dostępność (użytkownicy słabowidzący nie powiększą strony). Problem zoomu na inputach rozwiązuje się przez font 16px (sekcja 12), nie przez blokadę.
✓ Rób
  • Bazowy CSS = mobile, rozszerzaj @media (min-width)
  • Testuj na realnym urządzeniu, nie tylko w DevTools
  • Projektuj treść od najważniejszej do najmniej ważnej (kolumna)
✕ Unikaj
  • Desktop-first z nadpisywaniem przez max-width
  • Stałych szerokości w px na kontenerach
  • Poziomego scrolla całej strony (overflow)

2 · Layout, breakpointy i jednostki

Breakpointy (3–5 punktów wystarczy)

Nie celuj w konkretne modele telefonów — ustaw breakpointy tam, gdzie łamie się treść. Standardowy zestaw:

ZakresUrządzenieUżycie
0–480pxTelefon (portret)Baza — 1 kolumna
481–768pxTelefon poziomo / mały tablet2 kolumny w gridach
769–1024pxTabletNawigacja pozioma wraca
1025px+DesktopPełny layout, sidebary

Nowoczesne jednostki viewport: dvh / svh / lvh

100vh na mobile jest błędne — nie uwzględnia chowającego się paska adresu, przez co sekcja „na cały ekran" jest ucięta. Rozwiązanie: dynamic viewport height. Wsparcie ~95% przeglądarek, zawsze z fallbackiem.

/* fallback najpierw, potem nowoczesna jednostka */
.hero{
  min-height: 100vh;   /* stare przeglądarki */
  min-height: 100dvh;  /* dynamiczna — śledzi pasek adresu */
}
  • dvh — dynamiczna, zmienia się gdy pasek przeglądarki się chowa (najbezpieczniejsza dla pełnoekranowych sekcji)
  • svh — small, zakłada widoczny pasek (dobra gdy nie chcesz „skoków")
  • lvh — large, zakłada schowany pasek

Fluid grid bez media queries

Grid, który sam się zawija — z 1 kolumny na telefonie do wielu na desktopie, bez ani jednego breakpointu:

.grid{
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(260px, 1fr));
  gap: 1rem;
}
Container queries (@container) to kolejny krok: komponent reaguje na szerokość rodzica, nie ekranu — ta sama karta działa w sidebarze i na pełnej szerokości. Używaj do komponentów, media queries do layoutu strony.

3 · Typografia fluid

Zamiast skakać rozmiarem fontu na breakpointach, użyj clamp() — płynne skalowanie między minimum a maksimum. To standard 2025.

/* clamp(MIN, PREFEROWANE-zależne-od-ekranu, MAX) */
h1{ font-size: clamp(1.9rem, 5vw, 2.7rem); }
p { font-size: clamp(1rem, 1rem + 0.3vw, 1.125rem); }

  • Body min. 16px — mniejszy tekst męczy i (na iOS) wywołuje zoom inputów
  • Krótkie akapity — na wąskim ekranie blok 5+ linii wygląda jak ściana
  • Kontrast min. 4.5:1 dla normalnego tekstu (WCAG AA)
  • Unikaj light/thin font-weight na małych rozmiarach — słabo czytelne w słońcu

Czerwony (30px) — poniżej normy, łatwo chybić. Zielony (48px) — komfortowy. Niebieski (60px) — dla głównych akcji (CTA, „Kup").

Praktyczna zasada: cel min. 48×48px, odstęp min. 8px. Jeśli ikona wizualnie musi być mała, powiększ obszar dotyku niewidzialnym paddingiem:

  display: flex; align-items: center; justify-content: center;
}

5 · Thumb zone — gdzie kciuk sięga bez wysiłku

Większość ludzi trzyma telefon jedną ręką i obsługuje kciukiem. Steve Hoober zmapował „strefy kciuka": dół-środek jest łatwy, góra i dalekie rogi — trudne. Dlatego najważniejsze akcje idą na dół ekranu (stąd popularność bottom nav i sticky CTA).

🟡 średnio · środek
🟢 łatwo · dół
zielona — primary CTA, nawigacja żółta — treść, secondary czerwona — rzadkie akcje, logo
  • Dolne 40–50% ekranu — główne CTA, pasek nawigacji, kluczowe przyciski
  • Góra — logo, tytuł, akcje rzadkie (zamknij, ustawienia) — wymaga zmiany chwytu
  • Leworęczni — strefa lustrzana; primary CTA trzymaj wyśrodkowane, nie w rogu
  • Weryfikuj heatmapami (Hotjar, Clarity) na realnym ruchu — model to punkt startu, nie dogmat

6 · Przewijanie w prawo — carousel / scroll-snap

Poziomy scroll („swipe w prawo") to natywny mobilny gest. Idealny do: galerii produktów, kategorii, opinii, kart usług. Nowoczesny sposób to CSS Scroll Snap — działa bez JS, płynnie i dotykowo.

Slajd 2
Slajd 3
Slajd 4

Każdy slajd „zatrzaskuje się" na środku. Kropki pokazują pozycję. Brak biblioteki — czysty CSS.

Kod — kontener i slajdy

.carousel{
  display: flex;
  gap: 12px;
  overflow-x: auto;
  scroll-snap-type: x mandatory;        /* wymuś zatrzaskiwanie */
  -webkit-overflow-scrolling: touch;       /* płynny scroll iOS */
  overscroll-behavior-x: contain;          /* nie „przeciągaj" całej strony */
  scrollbar-width: none;                    /* ukryj scrollbar */
}
.carousel .slide{
  flex: 0 0 78%;                            /* szerokość slajdu — peek następnego */
  scroll-snap-align: center;               /* punkt zatrzasku */
}
✓ Rób
  • mandatory dla galerii (zawsze pełny slajd), proximity dla list
  • Pokaż „peek" następnego slajdu (78–85% szer.) — sygnał, że jest więcej
  • Dodaj kropki/wskaźnik pozycji + strzałki na desktopie
  • overscroll-behavior-x: contain — żeby scroll nie „uciekał" do strony
✕ Unikaj
  • Ukrywania kluczowej treści w karuzeli — ludzie rzadko swipują dalej niż 1–2 razy
  • Auto-przewijania bez pauzy (dezorientuje, łamie a11y)
  • Poziomego scrolla bez wizualnej wskazówki, że da się przewinąć
  • Ciężkich bibliotek JS gdy wystarczy CSS
Dostępność: respektuj prefers-reduced-motion, dodaj nawigację strzałkami klawiatury i nie chowaj w karuzeli treści krytycznej dla konwersji.

7 · Rozwijane elementy — accordion / progressive disclosure

Na małym ekranie nie zmieścisz wszystkiego naraz. Accordion (rozwijane sekcje) realizuje progressive disclosure — pokazujesz nagłówki, szczegóły dopiero po tapnięciu. Idealne do: FAQ, specyfikacji produktu, filtrów, długich treści, menu.

Demo — tapnij, żeby rozwinąć
Czym jest progressive disclosure? ▾
Technika pokazywania tylko niezbędnych informacji, a reszty na żądanie. Zmniejsza chaos i obciążenie poznawcze użytkownika.
Kiedy używać accordionu? ▾
Gdy masz dużo treści podzielonej na sekcje, a użytkownik potrzebuje tylko części naraz — FAQ, opisy, parametry, filtry.
Czy to dobre dla SEO? ▾
Tak — treść jest w HTML (tylko wizualnie ukryta), więc Google ją widzi i indeksuje. Inaczej niż przy ładowaniu na klik z JS.

Zbudowane na natywnym <details> — zero JS, dostępne z klawiatury, czytniki ekranu działają out-of-the-box.

Kod — natywny i dostępny (bez JS)

<details>
  <summary>Czym jest progressive disclosure? <span class="chev">▾</span></summary>
  <div class="body">Treść widoczna po rozwinięciu…</div>
</details>
summary{ cursor:pointer; min-height:48px; list-style:none; display:flex; justify-content:space-between; align-items:center; }
summary::-webkit-details-marker{ display:none; }   /* ukryj domyślny trójkąt */
.chev{ transition:transform .25s; }
details[open] .chev{ transform:rotate(180deg); }    /* obróć strzałkę */
✓ Rób
  • Nagłówek to <button>/<summary> + aria-expanded
  • Strzałka/ikona po prawej, obrót przy otwarciu jako sygnał stanu
  • Cały nagłówek klikalny (min. 48px), nie tylko ikona
  • Najczęstsze pytanie możesz zostawić rozwinięte na start
✕ Unikaj
  • Chowania treści, którą i tak każdy musi przeczytać (cena, dostawa)
  • Zagnieżdżania accordionów w accordionach
  • Ładowania treści dopiero na klik (gorzej dla SEO i a11y)
  • Braku wizualnego stanu otwarte/zamknięte

8 · Bottom sheet — panel wysuwany z dołu

Panel wysuwający się od dołu ekranu — w strefie kciuka. Zastępuje klasyczne modale (które na mobile lądują wysoko, poza zasięgiem). Idealny do: opcji, filtrów, wyboru, szybkich akcji, szczegółów. To forma progressive disclosure dla akcji.

✓ Rób
  • Widoczny przycisk zamknięcia (X) + „grab handle" jako wskazówka
  • Scrim (przyciemnione tło) + zamykanie tapnięciem w tło
  • Przycisk Wstecz/swipe w dół też zamyka

9 · Sticky CTA — przyklejony przycisk akcji

Główne CTA przyklejone do dołu, widoczne przez cały scroll — zawsze w zasięgu kciuka. Na długich stronach i kartach produktu daje 8–15% mniej wyjść i wyższą konwersję. Klasyk e-commerce („Dodaj do koszyka") i landingów.

Kod — pasek przyklejony do dołu

.sticky-cta{
  position: sticky;        /* lub fixed dla całego viewportu */
  bottom: 0;
  padding-bottom: env(safe-area-inset-bottom);  /* notch / pasek iPhone */
  min-height: 56px;
}
Safe area: na iPhone z paskiem gestów używaj env(safe-area-inset-bottom) + <meta viewport ... viewport-fit=cover>, żeby przycisk nie chował się pod systemowym paskiem.
  • Jeden cel, jedno CTA — bez listy funkcji i opisów w pasku (rośnie cognitive load)
  • Przycisk Wstecz/zamknij jeśli pasek zasłania treść
  • Wsuwaj płynnie gdy staje się istotny, nie wrzucaj gwałtownie

10 · Nawigacja — hamburger vs bottom nav

11 · Gesty & swipe

Gesty są szybkie i naturalne, ale niewidoczne — dlatego nigdy nie mogą być jedyną drogą do akcji. Zasada: gest jako skrót, zawsze z widoczną alternatywą (przycisk).

GestTypowe użycieUwaga
Swipe poziomyCarousel, zakładki, usuń/archiwizujPokaż „peek" lub podpowiedź
Swipe w dółZamknij sheet/modal, odśwież (pull-to-refresh)Dodaj też przycisk X
Long-pressMenu kontekstowe, podglądMało odkrywalny — tylko skrót
Pinch / double-tapZoom zdjęć, mapyOczekiwany przy obrazach/mapach
  • Zawsze alternatywa — każda akcja gestem ma też widoczny przycisk
  • Nie przejmuj systemowych gestów — swipe od krawędzi = Wstecz w systemie
  • Feedback — wizualna reakcja na gest (przesuwa się, podświetla)
  • Strefa bezpieczna — interaktywne elementy z dala od krawędzi (kolizja z gestami OS)

12 · Formularze na mobile

Wpisywanie na telefonie jest uciążliwe — dobra optymalizacja formularzy to najprostszy wzrost konwersji. Właściwa klawiatura skraca czas wpisywania o ~30% i redukuje błędy o ~50%, a autofill podnosi konwersję o ~20%.

Właściwy type i inputmode = właściwa klawiatura

<!-- e-mail: klawiatura z @ i .pl -->
<input type="email" autocomplete="email" inputmode="email">

<!-- telefon: klawiatura numeryczna (NIE type=number!) -->
<input type="tel" autocomplete="tel">

<!-- kwota / kod pocztowy: cyfry bez strzałek-spinnerów -->
<input type="text" inputmode="decimal">

<!-- kod SMS: auto-wpis z wiadomości -->
<input autocomplete="one-time-code" inputmode="numeric">
PoleUstawienie
E-mailtype="email" + autocomplete="email"
Telefontype="tel" (nie number — psuje formatowanie)
Imię / nazwiskoautocomplete="name" / given-name
Kwota, PIN, kodinputmode="numeric" lub decimal
Kod z SMSautocomplete="one-time-code"
Adres, miastoautocomplete="street-address", address-level2
Pułapka iOS — zoom na inpucie. Gdy font inputa < 16px, Safari sam powiększa stronę po kliknięciu w pole (i nie wraca). Rozwiązanie: font-size: 16px na wszystkich polach. Nie blokuj tego przez maximum-scale (łamie a11y).
input, select, textarea{ font-size: 16px; }  /* zapobiega auto-zoom iOS */
✓ Rób
  • Jedna kolumna, pola pełnej szerokości, min. 48px wysokości
  • Włącz autocomplete na każdym polu
  • Etykiety nad polem (nie placeholder zamiast etykiety)
  • Walidacja inline + jasny komunikat błędu
✕ Unikaj
  • Tylu pól ile w wersji desktop — tnij do minimum
  • type="number" do telefonów/kart/kodów
  • Placeholdera jako jedynej etykiety (znika po wpisaniu)
  • CAPTCHA i pól, których nie musisz zbierać na mobile

13 · Obrazy & media

Obrazy to zwykle najcięższy element strony i główny winowajca wolnego LCP na mobile. Nowoczesne formaty + responsywne dostarczanie tną wagę o 50–80%.

AVIF
Najlepsza kompresja
WebP
~97% wsparcia, −25–35% vs JPEG
srcset
Właściwy rozmiar na urządzenie

Responsywne obrazy — srcset + sizes

<img
  src="foto-800.jpg"
  srcset="foto-400.jpg 400w, foto-800.jpg 800w, foto-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw, 50vw"
  width="800" height="600"     <!-- ZAWSZE — rezerwuje miejsce, zero CLS -->
  loading="lazy" decoding="async"
  alt="Opis obrazu">

Format z fallbackiem przez <picture>:

<picture>
  <source type="image/avif" srcset="foto.avif">
  <source type="image/webp" srcset="foto.webp">
  <img src="foto.jpg" alt="…" width="800" height="600">
</picture>
✓ Rób
  • width+height (lub aspect-ratio) na każdym obrazie — zero CLS
  • loading="lazy" na obrazach poniżej ekranu
  • AVIF/WebP z fallbackiem; CDN obrazów
✕ Unikaj
  • lazy na obrazie LCP (hero) — opóźnia render
  • Serwowania desktopowych 3000px na telefon
  • Autoodtwarzanego wideo z dźwiękiem na mobile

14 · Wydajność — Core Web Vitals (2025/2026)

Google ocenia stronę osobno na mobile, na 75. percentylu realnego ruchu. To czynnik rankingowy. Tylko ~48% stron mobilnych przechodzi wszystkie trzy metryki — to realna przewaga konkurencyjna.

LCP ≤ 2,5s
Largest Contentful Paint — ładowanie
INP ≤ 200ms
Interaction to Next Paint — responsywność
CLS ≤ 0,1
Cumulative Layout Shift — stabilność
Zmiana: w 2024 INP zastąpił FID jako metryka responsywności — mierzy opóźnienie wszystkich interakcji, nie tylko pierwszej. Ciężki JavaScript najmocniej psuje INP na słabszych telefonach.

Jak realnie poprawić każdą metrykę

  • LCP — optymalizuj obraz/nagłówek hero, fetchpriority="high", preload fontu, CDN, mniej blokującego CSS
  • INP — tnij i dziel długie zadania JS, mniej zewnętrznych skryptów, content-visibility, debounce
  • CLS — wymiary obrazów/wideo, rezerwacja miejsca na reklamy/embedy, font-display: swap, nie wstawiaj treści nad istniejącą
Mierz realnych użytkowników: PageSpeed Insights (dane CrUX) + Search Console (raport Core Web Vitals) + lokalnie Lighthouse w trybie mobile z throttlingiem. Lab ≠ field — licz się z polem.

15 · Dostępność & detale techniczne

Drobiazgi, które odróżniają stronę „działa" od „dopracowana". Większość to jedna linia kodu.

Ruch — szanuj prefers-reduced-motion

@media (prefers-reduced-motion: reduce){
  *{ animation:none !important; transition:none !important; scroll-behavior:auto; }
}

Stany dotyku zamiast hover

Na telefonie nie ma „hover" — efekty hover albo nie działają, albo „przyklejają się". Projektuj stan :active i używaj hover tylko warunkowo:

/* hover tylko tam, gdzie urządzenie faktycznie go ma */
@media (hover: hover){ .btn:hover{ background:#333; } }
.btn:active{ transform:scale(.97); }   /* feedback dotyku */

Inne detale

  • Tap highlight — kontroluj -webkit-tap-highlight-color (domyślny szary box bywa brzydki)
  • Safe area — env(safe-area-inset-*) + viewport-fit=cover dla notcha/paska gestów
  • Focus widoczny — nie usuwaj :focus-visible (nawigacja klawiaturą/switch)
  • aria-expanded — na accordionach, hamburgerze, dropdownach (stan dla czytników)
  • Kontrast — min. 4.5:1 tekst, 3:1 elementy UI i ikony (WCAG AA)
  • Język — <html lang="pl"> dla poprawnego czytania i autokorekty

16 · Checklist przed publikacją

Szybka kontrola każdej strony przed wdrożeniem na produkcję.

Fundamenty

  • Viewport meta obecny, zoom nie zablokowany
  • CSS mobile-first, brak poziomego scrolla całej strony
  • Pełnoekranowe sekcje używają dvh, nie vh
  • Body text min. 16px, kontrast ≥ 4.5:1

Dotyk & interakcja

  • Wszystkie cele dotykowe ≥ 48px, odstęp ≥ 8px
  • Główne CTA w dolnej strefie (zasięg kciuka)
  • Carousele: scroll-snap + wskaźnik pozycji + overscroll contain
  • Accordiony: natywne/ARIA, cały nagłówek klikalny, stan widoczny
  • Każdy gest ma widoczną alternatywę (przycisk)

Formularze

  • Poprawny type/inputmode (tel, email, numeric…)
  • autocomplete na każdym polu, font pól = 16px
  • Etykiety nad polem, walidacja inline

Wydajność

  • Obrazy: WebP/AVIF, srcset, width+height, lazy poniżej ekranu
  • Hero/LCP nie jest lazy, font preload + swap
  • LCP ≤ 2,5s · INP ≤ 200ms · CLS ≤ 0,1 (test mobile + throttling)
  • Sprawdzone w PageSpeed Insights i Search Console

Detale

  • prefers-reduced-motion obsłużone
  • Hover tylko pod @media (hover:hover), jest stan :active
  • safe-area dla notcha/sticky CTA, focus widoczny
  • Przetestowane na realnym telefonie (iOS + Android)

Specyfikacja Optymalizacji Mobile · v1.0 · referencja produkcyjna dla agency-site.
